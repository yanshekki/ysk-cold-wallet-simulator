# CWS 1.1.6 (build 12)

YSK Limited · phone `hk.ysk.cws` · CWS Proxy `hk.ysk.cws.proxy`

Product: https://ysk.hk/products/ysk-cold-wallet-simulator

This note covers what landed after 1.1.5 (build 11): TON `SIGN_TX`, `SIGN_DATA`, and `GET_ADDRESS_PROOF` now hash and sign the same 32-byte values LedgerHQ/app-ton firmware hashes. It does not attach binaries. Signing identities and keystores are not in git. Seeds are not absolutely safe, and they are not hardware-wallet safe.

## English

CWS is a phone simulator for developers and wallet teams testing interoperability with selected Ledger, Trezor, and OneKey Bluetooth models. It is not a secure element. Ledger, Trezor, and OneKey do not endorse it. Do not use it to hold real digital assets.

**Seeds are not absolutely safe.** The public statement is [docs/security.md](https://github.com/yanshekki/ysk-cold-wallet-simulator/blob/main/docs/security.md). The 1.1.5 baseline still applies.

### What 1.1.6 changes

- TON `SIGN_TX` (INS `06`) is FIXED. The device parses LedgerHQ/app-ton `doc/TRANSACTION.md`, hashes the Wallet V4R2 order cell as `src/transaction/hash.c` / `src/common/cell.c`, and Ed25519-signs that 32-byte cell hash. The 98-byte reply is `len(sig)‖sig‖len(hash)‖hash` with that cell hash, not `sha256` of the uploaded APDU. Tag `0x00`, tag `0x01` (subwallet / wallet op), a payload cell ref, and a comment hint (`process_hints` type 0) are included. A payload without a matching hint is `BD00` because `GET_APP_SETTINGS` still reports `00`. A parse failure is `B010`. Tests: `tonCell.test.ts` (wrong-hash FAIL + canonical PASS).
- TON `SIGN_DATA` (INS `09`) is FIXED. Plaintext schema `0x754bf91b` signs `schema_crc ‖ timestamp ‖ cell_hash` as `src/crypto.c` `crypto_sign_sign_data` and `src/sign_data/sign_data_deserialize.c`. The returned hash field is the cell hash (`helper_send_response_sig_sign_data`). Unknown schemas are `B011`.
- TON `GET_ADDRESS_PROOF` (INS `08`) is FIXED. The digest is TON Connect `sha256("ton-proof-item-v2/" ‖ workchain_be32 ‖ address_hash ‖ domain_len_le32 ‖ domain ‖ timestamp_le64 ‖ payload)` then `sha256("\xff\xffton-connect" ‖ inner)` from `src/proof/proof_deserialize.c`. The address hash is `src/address.c` `pubkey_to_hash` (Wallet V4 data cell + root header). Witnesses verify over that 32-byte hash.
- Solana INS `21` / `22`, Bitcoin policy HMAC, and Ethereum clear-sign stay KEEP. Phantom unlock, Rabby scan, Avalanche Core X/P listing, and OKX asset display stay host-only KEEP. Proxy runtime adapters did not change.

### 1.1.6 改變了甚麼

- TON `SIGN_TX`（INS `06`）已 FIXED。裝置解析 LedgerHQ/app-ton `doc/TRANSACTION.md`，按 `src/transaction/hash.c`／`src/common/cell.c` 雜湊 Wallet V4R2 訂單 cell，並對該 32 位元組 cell hash 做 Ed25519 簽署。98 位元組回覆是 `len(sig)‖sig‖len(hash)‖hash`，hash 是該 cell hash，不是上傳 APDU 的 `sha256`。包括標籤 `0x00`、標籤 `0x01`（子錢包／wallet op）、payload cell 參照，以及註解提示（`process_hints` 類型 0）。有 payload 但提示不符時為 `BD00`，因為 `GET_APP_SETTINGS` 仍回報 `00`。解析失敗是 `B010`。測試：`tonCell.test.ts`（錯誤雜湊 FAIL 與規範 PASS）。
- TON `SIGN_DATA`（INS `09`）已 FIXED。明文 schema `0x754bf91b` 按 `src/crypto.c` `crypto_sign_sign_data` 與 `src/sign_data/sign_data_deserialize.c` 簽署 `schema_crc ‖ timestamp ‖ cell_hash`。回傳的 hash 欄是 cell hash（`helper_send_response_sig_sign_data`）。未知 schema 是 `B011`。
- TON `GET_ADDRESS_PROOF`（INS `08`）已 FIXED。摘要是 TON Connect 的 `sha256("ton-proof-item-v2/" ‖ workchain_be32 ‖ address_hash ‖ domain_len_le32 ‖ domain ‖ timestamp_le64 ‖ payload)`，再 `sha256("\xff\xffton-connect" ‖ inner)`，見 `src/proof/proof_deserialize.c`。地址雜湊是 `src/address.c` 的 `pubkey_to_hash`（Wallet V4 資料 cell 加根標頭）。見證對該 32 位元組雜湊驗證。
- Solana INS `21`／`22`、Bitcoin 策略 HMAC，以及以太坊 clear-sign 仍是 KEEP。Phantom 解鎖、Rabby 掃描、Avalanche Core 的 X／P 列出，以及 OKX 資產顯示，仍是只限主機的 KEEP。代理程式執行期轉接器沒有改動。
